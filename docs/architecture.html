So what is postmarketOS in this build? Not the operating system. This is Arch Linux ARM. pmOS shows up as three things: the kernel .config, a few modem/call daemons (q6voiced, 81voltd, bootmac), and — off the page — the wiki and pmaports that document how to make FP4 hardware work. It is a knowledge and parts donor, not the base.

If Omarchy ships official ARM (“dragon”)

Dragon is the presumed Omarchy-on-ARM effort — it isn't in this tree, so this maps what it could plausibly own against what it structurally cannot. The dividing line is simple: dragon is a desktop layer, and almost everything hard here is below the desktop.

Could converge on dragon

The desktop identity

  • Omarchy config & theming likelyIf dragon publishes ARM packages, moarchy's port-4x patch — the work of making x86 Omarchy build for aarch64 — largely goes away. Track dragon instead of porting each release.
  • Package sourcing likelyToday Omarchy is fetched and rebuilt for ARM locally. Dragon would provide that as a first-class target.
  • Compositor defaults partialHyprland tuning and keybinds could come from dragon — but a phone needs gestures and rotation a desktop config won't carry.
Stays ours / upstream regardless

Everything below the desktop

  • The whole phone shell staysGestures, on-screen keyboard, dialer, control center, SIM — moarchy-specific. A desktop ARM Omarchy has no mobile UI to hand us.
  • Kernel + all drivers staysThe SM6350 kernel and our audio/NFC/mic work are hardware enablement. No compositor project touches this; it belongs in mainline.
  • Firmware & Qualcomm stack staysBlobs, qrtr, rmtfs, qbootctl, the modem daemons — SoC-level, identical whatever renders on top.
  • Sensors, camera, modem, GPS stayshexagonrpc, megapixels, ModemManager glue — device plumbing, not desktop.
The honest headline: dragon could let us stop maintaining the desktop port and theming, and maybe the base package sourcing. It would not replace the phone shell, and it touches none of the hard hardware work — kernel drivers, firmware, modem, audio, NFC, sensors. Becoming “independent of postmarketOS” is a separate question: even with dragon, the pmOS-derived pieces (kernel config, call-audio daemons) and the SoC enablement knowledge stay in play until that work lands in mainline.

Sources verified against manifest.toml and the pkgbuilds on branch fp4-claude. The dragon column is reasoning, not a repo fact — no dragon deliverables were available to check against.
